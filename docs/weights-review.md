## A. Документация системы «как есть»

### A.0 Что вообще считается

Итоговое число — это `w` в `_dynamics.json` для пары **(сущность, патч)**. Оно складывается из баллов отдельных
строк патчноута. Балл строки:

```
балл = вес(тип строки) × направление × величина
```

* **тип** — к какой характеристике относится строка (`damage`, `cooldown`, `armor`, …). Определяется
  упорядоченной таблицей регулярных выражений по тексту строки, первое совпадение выигрывает.
* **вес** — число 0..1 из `data/rules/valve_weights.json`, «насколько Valve ценит эту характеристику».
  Получен из отдельного исследования (модель выявленных предпочтений, см. A.2–A.4).
* **направление** — `+1` бафф, `−1` нерф, `+0.5` new, `−0.5` del, `0` для rework / misc / qol.
* **величина** — среднее модулей процентов по бейджам строки, потолок 50 %, делённое на 25
  (то есть 25 % = 1.0). Строка без процентного бейджа = 1.0.

Значения **по патчам, не накопительно**: клетка = один патч.

### A.3 Как получается consensus

`consensus.py`:
1. Из каждого сигнала берётся одна колонка-число на тип, с порогом по объёму данных
   (L: ≥5 событий; B: ≥20 наблюдений; D: ≥30 баффов; E: ≥30 параметров; C: ≥30 пар; F: ≥30 нот).
2. Колонка `A_gold_per_unit` **исключена** из ранжирования (золото за единицу между типами несравнимо),
   в ранг идёт только `A_price_trend_%`.
3. Каждая колонка превращается в ранг: типы сортируются по значению, ранг = `i/(n−1)` ∈ [0,1].
4. `consensus` = среднее доступных рангов; `disagreement` = стандартное отклонение рангов;
   `reliable` = есть ≥3 сигнала.

Результат (надёжные): stun 0.76, lifesteal 0.72, crit 0.72, move_speed 0.63, damage 0.62, duration 0.61,
base_damage 0.60, armor 0.58, cooldown 0.58, attack_speed 0.52, silence 0.48, stats 0.47,
cast_range/mana_cost/cast_point 0.45, gold_xp 0.44, slow 0.43, health 0.42, charges 0.40, mana 0.30,
magic_res 0.28, projectile 0.26, range 0.24, vision 0.12.
Ненадёжные (<3 сигналов): respawn 0.97, chance 0.93, bkb_pierce 0.90, status_res 0.83, slow_res 0.80,
evasion 0.70, mechanic_flag 0.27, spell_amp 0.10.

### A.4 Как это применяется на сайте

* `data/rules/valve_weights.json` — таблица весов. Это **дословная копия** consensus, включая все восемь
  «ненадёжных» значений, **плюс три ручные добавки** без единого сигнала: `cost 0.45`, `turn_rate 0.2`, `other 0.4`.
* `patch/weights.py` — своя копия таблицы `CAT` (отличается от модельной только KV-шными вариантами написания,
  на прозе результат тот же), функция `classify()` и `row_score(text, tags, badge_html)`.
  Проценты вытаскиваются регуляркой `class="badge (buff|nerf)\d+">…%<`.
* `patch/elements.py`: `li()` вызывает `row_score` и передаёт в `_dyn_record_li()`, который копит сумму
  в `patches[версия]["w"]` (округление до 2 знаков на каждом шаге).
* `docs/data-format.md` — раздел «Dynamics "Weights" mode».
* `src/scripts.js`: `dynFmtW` (формат числа), `dynWeightTint` (заливка клетки, |w| каппится на 4),
  `dynWeightBar` (столбик на матрицах, тоже кап 4), `dynBuildPill` (переключает режим).

Масштаб на практике: 1 497 клеток с ненулевым `w`, медиана |w| = 0.48, максимум 4.54
(Brewmaster 7.40). То есть кап в 4 на отрисовке срезает единицы клеток.

## B. Найденные ошибки и слабые места

### B.1 КРИТИЧНО — `bkb_pierce` стоит первым в таблице и перехватывает чужие строки

`patch/weights.py`, `CAT[0]`: `("bkb_pierce", r"pierce|debuff immun|spell immun|magic immun|dispel")`.
Первое совпадение выигрывает, поэтому **любая** строка, где где-то встретилось слово «dispel» или «immune»,
получает вес 0.90 — самый высокий из реально встречающихся.

Факт: из 40 направленных строк, классифицированных как `bkb_pierce`, при отключении этого правила
21 стала бы `other`, 6 — `cooldown`, 3 — `damage`, по 2 — `magic_res`, `silence`, `move_speed`, и т.д.

Живой пример (Treant Protector, 7.41f):
`"Aghanim's Scepter: Decreases cooldown from 110/100/90 to 80/70/60s. When casting Overgrowth, Treant Protector dispels…"`
— это **строка про кулдаун**, но она весит 0.90 вместо 0.58.

Как чинить: опустить `bkb_pierce` ниже конкретных параметрических категорий (cooldown, mana_cost,
cast_range, damage, duration), а лучше — требовать, чтобы слово-триггер стояло в **начале строки** или
в её «параметрической части» (до слова increased/decreased/rescaled).

### B.2 КРИТИЧНО — «speed» → `projectile`, «steal» → `lifesteal`, «proc» → `chance`

* `projectile` = `r"projectile|missile|speed"`. Из 23 направленных строк этого типа **15 не содержат слов
  projectile/missile**: «Leap speed», «pull speed», «drag speed», «Roll Speed», «Bonus Speed», «Max Speed Increase».
  Это скорости перемещения (по смыслу ближе к `move_speed`, вес 0.63), а получают 0.26 — ошибка в 2.4 раза.
* `lifesteal` = `…|\bsteal\b`. Из 54 направленных строк 19 не содержат слова «lifesteal»: «Regen Steal»,
  «Restoration Steal», «Mana Steal», «Int Steal». Вес 0.72 — один из самых высоких.
* `chance` = `r"chance|\bproc|probability"`, вес **0.93**. Ловит «No longer procs Magic Stick»,
  «No longer increases block chance against towers» — то есть служебные оговорки получают почти максимальный вес.

### B.3 КРИТИЧНО — «ненадёжные» веса перенесены в продакшн как есть, причём наверх таблицы

Пять из шести самых больших весов (`respawn 0.97`, `chance 0.93`, `bkb_pierce 0.90`, `status_res 0.83`,
`slow_res 0.80`) построены на **одном-единственном сигнале B** — среднем уровне таланта. Сам `consensus.md`
помечает их как «Unreliable (< 3 signals)», но `valve_weights.json` берёт их без оговорок.

Хуже того, для `respawn` сигнал B — это 194 наблюдения, **100 % которых на уровне 25**. То есть
«ранг 1.0» здесь означает не «Valve ценит респаун», а «таланты на респаун бывают только на 25-м уровне»
— свойство дизайна талантов, а не оценка ценности. Тот же дефект у `cast_point` (72 наблюдения, 100 % на L25),
который в B стоит вторым, а в C/D/E оказывается в самом низу — отсюда `disagreement 0.42`, худший в таблице.

На сайте эти веса живые: строка «No longer levels with Reincarnation» весит 0.97.

Как чинить: либо не выгружать в `valve_weights.json` типы с <3 сигналами (ставить им `other`),
либо явно «сжимать» их к середине (см. E.3).

### B.4 КРИТИЧНО — сигналы консенсуса друг другу противоречат, а усредняются как согласные

Попарная корреляция рангов по типам, где обе колонки заполнены:

| пара | n | r |
|---|---|---|
| B_talent_level × F_base_nerf_% | 8 | **−0.80** |
| B_talent_level × D_buff_revert_% | 20 | **−0.42** |
| L_ladder_meanΔ × B_talent_level | 15 | **−0.38** |
| A_price_trend × B_talent_level | 10 | −0.26 |
| E_streaks × B_talent_level | 24 | −0.14 |
| D_buff_revert × E_streaks | 20 | +0.66 |
| D_buff_revert × F_base_nerf | 8 | +0.57 |
| L_ladder × D_buff_revert | 15 | +0.56 |
| остальные пары | | от −0.09 до +0.35 |

Две вещи: (1) сигнал B — главный по охвату (31 тип из 32) — **отрицательно** коррелирует почти со всеми
остальными; (2) положительно связанная группа D/E/F измеряет, по сути, одно и то же — «как часто Valve трогает
параметр», а не «насколько он ценен». Среднее по семи почти ортогональным и местами антикоррелированным
рангам — это не консенсус, а сглаживание к середине: у 24 надёжных типов итог укладывается в узкий
диапазон 0.12–0.76, и половина сидит между 0.40 и 0.63.

Честная формулировка: **модель статистически не обоснована как «единая шкала ценности»**. Она обоснована как
набор из семи отдельных описательных наблюдений о поведении Valve — и в этом качестве полезна.

### B.5 КРИТИЧНО — интерпретация знака у D, E, F, C принята без проверки

* **D**: «баффы быстро откатывают ⇒ рычаг ценный». Равновероятная альтернатива: «параметр шумный/мелкий,
  его крутят туда-сюда». Заметьте: по D на первом месте стоит `other` (58 %) — мусорная корзина классификатора.
  Это прямой намёк, что D измеряет частоту правок, а не ценность.
* **E**: то же самое, и снова `other` на первом месте с огромным отрывом (97.7 против 32.5 у второго места).
* **F**: «чаще нерфят, чем баффят ⇒ сильная характеристика». Но доля нерфов у большинства типов 36–48 %,
  то есть около 50/50; ранжирование по такому почти-константному признаку — это ранжирование шума.
  Плюс у F всего 8 типов проходят порог, и ранг `i/(n−1)` на восьми точках даёт шаг 0.14.
* **C**: «чаще на нерф-стороне ⇒ ценнее». Но конструкция C — декартово произведение всех баффов на все нерфы
  внутри (герой, патч), без учёта того, что это одна способность. У героя с 1 баффом и 5 нерфами получится
  5 пар, где бафф-тип посчитан 5 раз. Веса пар не нормируются.

Ни одна из четырёх интерпретаций не проверена обратным тестом.

### B.6 ВАЖНО — ранги несравнимы между колонками (разное покрытие типов)

Покрытие сигналов: L — 16 типов, B — 31, A_trend — 10, D — 20, E — 24, C — 24, **F — 8**.
Ранг `i/(n−1)` зависит от того, сколько типов попало в колонку. Тип, стоящий «в середине» по F,
получит 0.5 из 8 точек; тот же тип «в середине» по B получит 0.5 из 31 — но это совершенно разные
по надёжности половинки. Хуже: если типа нет в колонке, его отсутствие меняет ранги всех остальных.

Отдельно: **сигнал L использует свой собственный классификатор** (`weights_from_ladder.py`, 19 категорий
по именам KV-ключей), в котором вообще нет типов `mana_cost`, `cast_range`, `cast_point`, `silence`,
`vision`, `gold_xp`, `base_damage`, `magic_res`, `evasion`, `status_res`, `slow_res`, `spell_amp`.
То есть столбец L физически не может оценить половину таблицы — и это не отмечено как пропуск данных,
это выглядит как «сигнала нет».

### B.7 ВАЖНО — величина: одинаковое решение Valve даёт разный балл

Это самый заметный дефект **на сайте**. Примеры из собранных страниц (все — «Base Armor −1»):

| патч | строка | бейдж | балл |
|---|---|---|---|
| 7.39 | Base Armor decreased by 1 (стало 3) | −25 % | −0.58 |
| 7.39 | Base Armor decreased by 1 (стало 2) | −33 % | −0.77 |
| 7.39 | Base Armor decreased by 1 (стало 1) | −50 % | −1.16 |
| 7.38c | Base Armor decreased by 1 (стало −1) | нет | −0.58 |

Одно и то же решение Valve («минус один в броню») оценивается с разбросом в **2 раза** — просто потому,
что у одного героя брони было 4, а у другого 2. И −1.16 за одну единицу брони — это почти четверть
максимальной клетки во всём корпусе (4.54).

Сигнал F, кстати, уже даёт лекарство: типичный шаг Valve по типу (броня 1, MS 5, статы 2, base damage 3,
здоровье 0.5, мана 0.25, дальность 50). Но на сайте он не используется.

### B.8 ВАЖНО — нулевые бейджи выбрасываются из среднего, каппинг искажает

* Регулярка `_PCT_RE` ловит только `badge buffN` / `badge nerfN`. Бейдж `badge neutral">0%` **не ловится**.
  Строк с таким бейджем в корпусе **476**. Пример: Treant «Damage to Healing rescaled from 20 % to 10/15/20/25 %» —
  бейджи −50/−25/**0**/+25; считается среднее по трём (33.3), а не по четырём (25). Величина завышена на треть.
* Потолок 50 % срабатывает на **154 строках**. Пример: Octarine Core 7.41f
  «Recipe cost increased from 200 to 400. Total cost increased from 4900g to 5100g» — бейджи +100 % и +4 %,
  среднее 52 → упирается в потолок → величина 2.0 (максимум) → балл −0.90.
  Реально это подорожание предмета на 4 %. **Рецепт и тотал считаются как две равноправные величины.**
* Формульные строки (`li_formula`/`bf`) дают до 20 бейджей по уровням. Abaddon 7.41
  «Health Restoration Reduction changed from 35 %…»: бейджи от −29 % до +13 % по уровням 1..30,
  среднее модулей 17 → величина 0.7. Смысл «среднего модуля разнонаправленных изменений» неясен.
* Строки **без процента** — 906 из 3 685 направленных (**25 %**), им ставится величина 1.0 (= 25 %).
  Они дают **27 % всего |score|** по корпусу. То есть четверть сигнала — это константа-затычка.

### B.9 ВАЖНО — направление `±0.5` для new/del фактически не работает

`_DIR` проверяет теги в жёстком порядке `buff, nerf, new, del` и берёт первый найденный. По корпусу:

| набор тегов | строк | какое направление применится |
|---|---|---|
| buff | 1 471 | +1 |
| nerf | 1 405 | −1 |
| rework | 577 | 0 (строка игнорируется) |
| buff + new | 404 | **+1**, не +0.5 |
| nerf + del | 327 | **−1**, не −0.5 |
| misc | 239 | 0 |
| new (один) | 61 | +0.5 |
| qol | 43 | 0 |
| прочие | 17 | |

Итог: правило «±0.5» реально применяется к **61 строке из 4 544 (1.3 %)**, а `del`-строк без `nerf`
в корпусе **нет вообще**. Документация в `docs/data-format.md` описывает поведение, которого в данных не происходит.

### B.10 ВАЖНО — реворки стоят 0, а это 577 строк (13 % корпуса)

Реворк — часто самое крупное решение Valve по герою (сигнал G: 3 138 таких событий за историю,
Invoker переделывали 54 раза). Сейчас реворк не влияет на балл вообще. Пример:
Treant 7.41f, талант 10 уровня «+3 Living Armor Heal per Second» заменён на «+3s Living Armor Duration» — балл 0.
При этом Treant 7.40 (6 del + 4 new + 8 buff + 3 nerf + 6 rework) даёт **+3.6**, потому что баффов оказалось
больше, чем нерфов, — а по сути это был крупный реворк героя, и знак «+3.6» подан как факт.

### B.11 ВАЖНО — модель без контекста: ульта, уровень таланта, база vs талант

Балл строки не зависит от того, где именно изменение:

* Spectre 7.40b: «Illusion Damage 20/30/40/50 % → 32/38/44/50 %» (ключевая способность) = **+0.80**;
  «Level 10 Talent: Desolate Damage +10 → +12» (талант 10 уровня, +2 единицы) = **+0.50**.
  Талант десятого уровня получил 62 % от веса ядровой переработки способности.
* Ульты, аспекты, Shard/Scepter, база и таланты — всё в одном котле, хотя сигналы L и B в самой модели
  построены ровно на том, что **место на лестнице доступа = цена**. Эта информация есть, но на сайте не используется.
* Уровень способности не учитывается: −50 % на первом ранге и −50 % на четвёртом весят одинаково,
  хотя сам `b()` в `patch/badges.py` уже исходит из противоположного (правило max-rank, front-loaded,
  back-loaded, early-game-cut — всё это про то, что уровни неравнозначны).

### B.12 ВАЖНО — герои и предметы считаются одной шкалой

Веса выведены почти целиком из геройских данных: C/D/E строятся на `scope in (ability, hero_base, talent)`
(11 408 строк из 24 215), F — только hero_base, B и L — только таланты и KV героев. Предметные строки
(3 118 событий) участвуют только в сигнале A, который в ранг попадает лишь трендом.
При этом `items_dyn` на сайте использует ту же таблицу. Тип `cost` — центральный для предметов —
**весов из данных не имеет вообще**, он вписан вручную (0.45).

### B.13 МЕЛОЧЬ, но стоит знать

* `mechanic_flag: 0.27` в `valve_weights.json` — мёртвая запись: сайтовая `CAT` этот тип не порождает никогда.
* Округление `round(score, 2)` на каждой строке **и** `round(sum, 2)` на каждом добавлении в
  `_dyn_record_li` — накопленная ошибка до ~0.01 на клетку. Незначительно, но это лишнее округление.
* `"Now costs 35 mana"` классифицируется как `mana` (0.30), а не `mana_cost` (0.45): регулярка
  `mana_cost` требует буквально «mana cost».
* `"Minimum damage block decreased from 20 to 10"` — это защитная характеристика, а получает вес `damage` 0.62
  и даёт −1.24, самую большую строку Treant 7.41f.
* `"Invisibility linger when leaving trees decreased from 2s to 1s"` → `other` (0.40), хотя это `duration` (0.61).
* `br()` (диапазон урона) считает процент по середине диапазона — для весов это нормально, просто отметить.
* `README.md` модели говорит «123 патча»; фактический `events.json` — **117 патчей**.
  Мелкое расхождение в документации.

### B.14 Главная проверка: даёт ли модель что-то сверх простого счётчика

Корреляция `w` с наивным счётчиком по 1 502 клеткам `_dynamics.json`:

* `corr(w, buff + new − nerf − del)` = **0.858**
* `corr(w, buff − nerf)` = **0.846**

То есть вся конструкция «веса × направление × величина» объясняет примерно **26 % дисперсии** сверх того,
что даёт бесплатный подсчёт «баффов минус нерфов». Причина арифметическая: разброс весов (0.12..0.97,
а на 90 % строк — 0.40..0.62) намного уже разброса количества строк, а средняя величина = 0.86 при медиане 0.92,
то есть почти константа. Вклад в |score| распределён по количеству строк, а не по весу:
damage 17.7 % (603 строки), cooldown 10.5 % (451), **other 10.0 % (674)**, health 8.1 % (356).

Это тот же диагноз, по которому была забракована старая модель `hero-weights-calibrated-20260804`.
Подчёркиваю: сейчас это не повод выбрасывать модель, но повод не выдавать `w` за «объективный вес»,
пока пункты B.7–B.11 не исправлены — сейчас число почти целиком определяется тем, **сколько строк** написал Valve.

## C. Что реально видно в данных (закономерности)

Ниже — только то, что подтверждается минимум двумя независимыми сигналами.

**1. Кулдаун — самый «неотпускаемый» рычаг.** E: 32.5 серии на 100 параметров (второе место после мусорного
`other` 97.7). D: 35 % нерфов кулдауна позже откатываются — максимум среди содержательных типов.
C: самая частая сделка Valve вообще — «кулдаун (бафф) ↔ урон (нерф)», 111 случаев, и зеркальная 91.
При этом по лестнице L кулдаун ползёт **вниз** (−0.58): Valve охотно раздаёт скидки на кулдаун ранним гейтам.

**2. Броня и скорость атаки — дорогие и «повышаемые».** L: armor +1.91 (11 событий), attack_speed +1.79 (7) —
два лидера по подъёму на лестнице. A: броня — самая дорогая характеристика в прайс-листе, 246.8 золота
за единицу против 32.9 за урон. F: типичный шаг Valve по броне — ровно ±1.
Оговорка: у L обоих типов очень маленькая база наблюдений.

**3. Мана, дальность и обзор отдаются дёшево.** L: mana −1.65, projectile −1.20, range −0.78 —
Valve систематически спускает их вниз по лестнице. A: мана в предметах стоит 5.7 золота за единицу,
mana_regen подешевел на 58 % за историю. C: vision на нерф-стороне всего в 28 % сделок —
Valve почти никогда не «платит» обзором. D: range откатывается в 9 % случаев, vision — 0 %.
Консенсус: vision 0.12, range 0.24, magic_res 0.28, mana 0.30 — низ таблицы, и это согласованный низ
(disagreement 0.09–0.28).

**4. Cast point — то, что Valve однажды поставил и больше не трогает.** D: 1 % баффов откатывается,
медиана до отката 43 патча (при типичных 14–26). E: 8.7 серий на 100. Но B ставит его на 25-й уровень (100 %).
Это самый «расколотый» тип в таблице (disagreement 0.42) и хороший пример того, что B меряет не ценность.

**5. Урон — рабочая лошадка, а не редкость.** Больше всего событий во всех сигналах: L 137 ходов,
B 17 924 талант-стороны, C 633+601 сделки, E 1 041 параметр. Нерф-сторона у урона 49 % — ровно половина,
то есть Valve одинаково часто им платит и его отбирает. Это «валюта», а не «сокровище».

**6. Цены в предметах менялись направленно.** Подорожали: движение (+66 %), магрезист (+39 %), урон (+16 %),
agility (+17 %, 89.4 → 104.6), strength (+18 %, 112.6 → 132.6). Подешевели: mana_regen (−58 %),
лайфстил (−26 %), all_stats (−22 %), health (−17 %), health_regen (−17 %). Читается как «Valve сделал
мобильность и выживание через резисты дороже, а прямое восстановление — дешевле».

**7. Valve чаще всего переделывает сложных героев, а не слабых.** G: Invoker 54, Omniknight 53, Io 46,
Batrider 41, Chen 39. Способности-рекордсмены — Chen/Holy Persuasion 13, Nyx/Vendetta 12,
Omniknight/Hammer of Purity 12. Это не про «баланс», а про «конструкция не работает».

**8. Базовые шаги Valve стандартизированы.** F: MS ±5, base damage ±3, статы ±2, броня ±1,
реген здоровья ±0.5, мана ±0.25, дальность ±50. Это, на мой взгляд, самая полезная числовая находка
всего исследования — готовая единица нормировки (см. E.1).

## D. Какие изменения важнее для итогового балла — сейчас и как должно быть

**Сейчас балл героя за патч определяется, в порядке убывания влияния:**

1. **Количеством строк** (r = 0.86 с наивным счётчиком). Пять мелких правок перевешивают один реворк ульты.
2. **Величиной процента** — но только для строк с бейджем, и с двумя искажениями: мелкие базовые
   значения раздувают процент (броня 2→1 = −50 %), а 0 %-уровни выбрасываются из среднего.
3. **Весом типа** — в узком диапазоне, у 90 % строк 0.40..0.62; влияние минимальное, кроме выбросов
   (`chance` 0.93, `respawn` 0.97, `bkb_pierce` 0.90, `vision` 0.12), которые почти всегда ошибочны (см. B.1–B.3).

**Что в балл не попадает вообще:**

| Фактор | Сейчас | Должно быть |
|---|---|---|
| Реворк способности | 0 | крупное событие; знак может быть неизвестен, но величина большая |
| Ульта vs первая способность | одинаково | ульта дороже |
| Уровень таланта (10 vs 25) | одинаково | 25-й весит больше (это прямо утверждает сигнал B) |
| База vs талант vs Shard/Scepter/аспект | одинаково | лестница доступа = цена (сигналы L и B ровно об этом) |
| Какой ранг способности изменился | одинаково | max-rank важнее (это уже есть в `b()`, но не в весах) |
| Изменение только у аспекта/Shard | как полноценное | частичный охват — меньше |
| Типичный шаг Valve по типу | не учитывается | нормировка величины (сигнал F даёт цифры) |
| Герой vs предмет | одна таблица | у предметов своя экономика (`cost` — ключевой тип) |
| Ранняя/поздняя игра | не учитывается | см. правила `b()`: early-game-cut уже признан значимым |

## E. Предложения по улучшению

### E.1 Нормировать величину «типичным шагом Valve», а не процентом (приоритет 1, трудоёмкость средняя)

Проблема B.7. Вместо процента от старого значения использовать отношение к типичному шагу Valve
по этому типу — цифры уже посчитаны в сигнале F (`fgh_scopes.json`).

```
величина = |Δ| / typical_step(type)     для абсолютных изменений (база, броня, MS, статы)
величина = |Δ%| / typical_pct(type)     для процентных
```
где `typical_step`: armor 1, move_speed 5, stats 2, base_damage 3, health_regen 0.5, mana_regen 0.25,
attack_range 50; `typical_pct` из сигнала C (медиана |%| по типу): damage 17–18 %, cooldown 17–20 %,
mana_cost 11–14 %, health 22–25 %, cast_point 40–43 %.

Тогда «Base Armor −1» всегда даёт величину 1.0 у любого героя, а «cast point −10 %» перестаёт весить
столько же, сколько «damage −10 %», хотя Valve двигает cast point шагами по 40 %.

**Побочный эффект:** можно убрать потолок 50 % (он нужен только из-за неустойчивости процента на малых числах)
и заменить его мягким сжатием, например `min(величина, 3)`.

### E.2 Починить классификатор (приоритет 1, трудоёмкость низкая)

Минимальный набор правок в `patch/weights.py`:

1. Опустить `bkb_pierce` после всех параметрических категорий, или требовать совпадения в начале строки.
2. `projectile`: убрать `speed`, оставить `projectile|missile`; добавить в `move_speed` паттерн
   `\bspeed\b` **без** «attack speed» (attack_speed уже стоит выше).
3. `lifesteal`: заменить `\bsteal\b` на `lifesteal|life steal|spell lifesteal`; «Regen Steal»,
   «Mana Steal» отправить в `health`/`mana`.
4. `chance`: убрать `\bproc` из ловли, либо дать типу вес `other` до появления второго сигнала.
5. `mana_cost`: добавить `costs? \d+ mana|mana per`.
6. `duration`: добавить `linger|lasts for`.
7. Добавить отдельный тип `damage_block` (или относить «damage block» к `armor`).
8. Ввести приоритет «первое совпадение в параметрической части строки» — то есть искать тип в тексте
   **до** первого глагола (increased/decreased/rescaled/changed/replaced), а не по всей строке.
   Это одним движением снимает большую часть ложных срабатываний из B.1–B.2.

**Обязательно:** после правки прогнать сравнительный дамп «было/стало» по всем `dist/patches/*.html`
и глазами просмотреть строки, у которых тип изменился (их будет порядка 100–150).

### E.3 Обрезать доверие к ненадёжным весам (приоритет 1, трудоёмкость минимальная)

В `valve_weights.json` для типов с <3 сигналами заменить значение на сжатое к середине:

```
w_final = w_other + (w_consensus − w_other) × k,   k = min(1, n_signals / 3)
```
Тогда `respawn` 0.97 → 0.59, `chance` 0.93 → 0.58, `bkb_pierce` 0.90 → 0.57, `evasion` 0.70 → 0.60.
Ручные `cost`/`turn_rate`/`other` пометить в файле отдельным блоком `"manual"`, чтобы их нельзя было
спутать с выведенными из данных.

### E.4 Контекстные множители (приоритет 2, трудоёмкость средняя)

Умножать балл строки на множитель места. Предлагаемые значения — не с потолка: они выводятся
из шага лестницы доступа в самой модели (8 ступеней от base до talent25).

| Контекст | Множитель | Обоснование |
|---|---|---|
| Ульта | ×1.3 | ульта — всегда максимальный гейт по уровню героя |
| Первая/вторая способность | ×1.0 | базовая линия |
| Талант 10 | ×0.6 | ступень 1 из 7 |
| Талант 15 | ×0.8 | ступень 3 |
| Талант 20 | ×1.0 | ступень 5 |
| Талант 25 | ×1.2 | ступень 7; сигнал B прямо говорит, что Valve ставит туда самое сильное |
| Аспект (facet) | ×0.8 | ступень 2, и затрагивает не всех игроков героя |
| Shard | ×0.9 | ступень 4 |
| Scepter | ×1.0 | ступень 6 |
| Базовая характеристика героя | ×1.0 | |

Данные для контекста на сайте **уже есть**: `elements.py` знает, в каком блоке строка
(`ability_block`, `talents-block`, `facet-block`, `is-innate`), а префикс «Level N Talent:» разбирается
регуляркой `_TALENT_PREFIX_RE`. Нужно только протащить контекст в `row_score()`.

### E.5 Дать реворкам ненулевую величину (приоритет 2, трудоёмкость низкая)

Сейчас 577 строк (13 %) невидимы. Варианты:
* **(а)** Реворк = событие без знака, но с «массой»: копить рядом с `w` отдельный ключ `wr`
  (сумма весов реворк-строк) и показывать его как второй, серый столбик/цифру. Знак не выдумывается.
* **(б)** Реворк = ±0 в балле, но клетка помечается рамкой/точкой «здесь был реворк».
* **(в)** Приписать реворку знак по бейджам внутри панелей «было → стало», если они есть.

Рекомендую **(а)** — честно и не ломает существующую шкалу.

### E.6 Отдельная таблица весов для предметов (приоритет 2, трудоёмкость средняя)

Данные для неё есть и не используются: сигнал A даёт прямые цены в золоте за единицу по 17 характеристикам,
плюс 3 118 предметных событий в `events.json`. Предлагаемая схема: для предметных строк величина
считается **в золоте**, а не в процентах:

```
балл_предмета = (Δ_характеристики × цена_за_единицу(A)) / цена_предмета
```
Это сразу решает проблему Octarine (B.8): +200 золота к тоталу 5100 даст 0.04, а не максимальный нерф.
А `cost` перестаёт быть ручным весом — он становится знаменателем.

### E.7 Новые сигналы из уже имеющихся данных (приоритет 3)

1. **Сигнал I — «сколько патчей подряд тип не трогают»** из `events.json`: обратная величина
   к частоте правок. Разделяет «часто трогают, потому что важно» и «часто трогают, потому что шумно».
2. **Сигнал J — курс обмена из C**: сейчас C использует только *долю* нерф-стороны, а в
   `cde_dynamics.json` лежат пары с `buff_pct` и `nerf_pct`. Отношение `nerf_pct/buff_pct` по типам —
   это буквально обменный курс Valve («X % урона = Y % кулдауна»). Это самый прямой путь к настоящим
   относительным весам, и он сейчас просто выброшен.
3. **Сигнал K — совместная встречаемость типов в одном пакете правок**: если Valve всегда правит
   тип X вместе с Y, это одна характеристика, а не две (полезно для схлопывания классификатора).
4. **Сигнал L' — распределение по гейтам в текущем KV** (не переезды, а статика): сколько эффектов
   каждого типа живёт на каждом гейте прямо сейчас. Даёт оценку той же лестницы на порядок большем объёме,
   чем 337 переездов.

### E.8 Валидация (приоритет 1 по важности, трудоёмкость средняя)

Без этого все улучшения — вкусовщина. Три проверки, все выполнимы на имеющихся данных:

1. **Обратный тест по сигналу D.** Гипотеза: чем больше |балл| строки, тем выше вероятность, что Valve
   откатит её в следующих патчах. Взять 11 408 численных событий, посчитать балл по нынешней формуле
   и построить кривую «балл → доля откаченных за 5 патчей». Если кривая плоская — формула ничего не предсказывает.
   Это единственный доступный **внешний** критерий, и он не зависит от винрейтов.
2. **Согласие с ручной разметкой.** Взять 100–150 строк вручную и проставить «ценность» в трёх
   градациях (мелочь / заметное / крупное). Считать ранговую корреляцию с баллом. Порог приличия — ρ ≥ 0.6.
3. **Тест на «сверх счётчика».** Повторять `corr(w, buff−nerf)` после каждого изменения формулы.
   Сейчас 0.846; цель — опустить ниже 0.7 (то есть модель должна начать говорить что-то своё).
   Если после E.1/E.2/E.4 корреляция остаётся выше 0.85 — значит, веса не нужны и достаточно счётчика.

## F. Спорные вопросы — нужно решение владельца

**F.1. Что вообще означает число `w`?**
Сейчас смешаны две разные вещи: «насколько сильно Valve изменил героя» (объём работы) и
«насколько герою стало лучше/хуже» (баланс). Варианты:
* (а) оставить одну шкалу «нетто-баланс» (знак важен);
* (б) две шкалы: `w` — нетто-баланс, `v` — объём/значимость правок без знака (тогда реворк попадает в `v`);
* (в) только объём.

**Рекомендация: (б).** Реворки и новые способности перестанут проваливаться в ноль, а знак останется честным.

**F.2. Оставлять ли ненадёжные веса?**
* (а) оставить как есть — риск, что `chance 0.93` будет и дальше портить случайные строки;
* (б) сжать к `other` по формуле из E.3;
* (в) выкинуть тип в `other`, пока не появится 3 сигнала.

**Рекомендация: (б)** — мягко и обратимо.

**F.3. Величина — процент или шаг Valve?**
* (а) процент (как сейчас) — интуитивен, но ломается на малых числах;
* (б) шаг Valve — устойчив, но «−1 брони = 1.0» не читается интуитивно с бейджа;
* (в) гибрид: шаг Valve для базовых характеристик с малыми целыми значениями (броня, статы, MS, реген),
  процент для остального.

**Рекомендация: (в).**

**F.4. Нужно ли сохранять единую таблицу весов для героев и предметов?**

**Рекомендация: разделить.** У предметов есть естественная единица — золото, и она уже посчитана (сигнал A).

**F.5. Считать ли по-прежнему только по патчам, не накопительно?**
Здесь я согласен с принятым решением: накопительная линия зависела бы от начала окна. Но стоит
отдельно добавить агрегат «за мажорную версию» (7.41 плюс все её подпатчи одной цифрой) — это то,
что интуитивно ищет читатель.

**F.6. Чей уровень способности брать за «истину» для величины?**
`b()` уже сложно и осознанно решает, что определяет направление (max-rank, front-loaded, back-loaded,
early-game-cut). Веса же берут среднее по уровням. Это два разных ответа на один вопрос.

**Рекомендация:** привести к одному — брать величину на том же уровне, на котором `b()` определил направление.
